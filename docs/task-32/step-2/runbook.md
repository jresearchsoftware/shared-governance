# Owner setup and controlled trial — for a later authorized execution

**Do not run this setup under Step 2.** It prepares owner actions after independent
non-approving review and a later owner Decision authorizing temporary project
creation/settings application and trials. It never instructs Codex to edit live
projects. Use the [capture sheet](capture-sheet.md) as the record; stop at an
unavailable setting rather than inventing an API or changing credentials.

Each numbered item is one action. Complete it and record its observed result
before the next. The client may show different labels; use only supported visible
controls. Record unavailable controls and comparability limits. Do not change
global/workspace settings merely to force an ideal experiment.

## Setup

1. Record the later owner Decision authorizing this trial, the reviewed prototype
   commit, client surface/date, account/workspace and visible model/effort selection.
2. Open a blank capture sheet for the first case pair.
3. Record personal instructions, memory/context controls and GitHub read access
   that may affect this account; record observations without copying sensitive data.
4. Create a new empty temporary ChatGPT project named `Task32 control C1`.
5. Choose isolated/project-only memory at creation **if the supported UI offers
   it**; otherwise record that isolation is unavailable and the result is confounded.
6. Confirm the control has no project-specific Instructions or Sources; retain
   comparable higher-priority/account context. Record the visible empty state.
7. Create a new empty temporary project named `Task32 experiment C1`.
8. Give it the same supported memory/context choice as the control.
9. Select the same visible model/effort in both projects; record unavailable
   telemetry instead of guessing the actual serving model.
10. Confirm both expose comparable GitHub read operations, including file/Issue/
    PR and CI access. Do not broaden permissions or reconnect credentials for the test.
11. Open [the complete Instructions artifact](shared-governance-instructions.md)
    at the independently reviewed prototype commit, not a moving branch preview.
12. Paste only the contents of its sole `markdown` block into the experimental
    project's supported Instructions field and save. If no such field exists,
    record **UNQUALIFIED — setup unsupported** and stop this pair; a chat message
    or Source upload is a different intervention and cannot replace it silently.
13. Reopen the saved field and compare its full text with the reviewed artifact.
    Record exact/truncated/changed/unavailable readback. Never trim critical rules
    to fit. A displayed correct field proves settings text, not model application.
14. Leave Sources empty in both projects. Do not add prior chats, reports or
    policy snapshots; the experiment must initiate its GitHub route itself.

There is no verified existing Shared Governance field to replace or diff. This
creates a temporary experiment only after later authorization. Record its actual
empty-to-text settings delta; do not call preparation a live no-op or deployment.

## A paired case

1. Select one case and its preconditions from [cases](cases.md).
2. Choose the pair's order before observing answers: alternate control-first and
   experiment-first across cases; record order so it cannot be cherry-picked.
3. Start a fresh chat inside the first selected project.
4. Send the exact case prompt, with the same URL/head/fixtures for both arms.
   Include: “Read-only trial; do not publish, mutate, launch, merge or close.”
5. Preserve the answer and visible tool input/results or transcript. Record
   inaccessible tool details as gaps; final self-reported reads alone are not proof.
6. Start a fresh chat inside the second project.
7. Send the identical prompt and fixture without the first answer or evaluator notes.
8. Preserve its answer/tool evidence in the same way.
9. Independently compare each answer with the case's primary source and expected
   boundary; complete each arm's sheet before comparing the arms.
10. Record the pair's difference, including equal performance, failed bootstrap,
    missing tools or memory confounds. Retain unfavorable trials.

For each subsequent case, use a new empty pair of projects and repeat Setup,
using the appropriate case ID. Project-level memory can carry earlier chats even
when each chat is fresh. If the owner chooses to reuse a pair, record the prior
case context and classify the result as confounded; do not claim a clean comparison.
Do not turn a failed answer into a PASS by prompting it with missing expected rules.
An exploratory corrective follow-up is a separately labelled observation with
both prompts retained, not the initial trial result. No agent runs these cases here.

## Small trial and interpretation

Run C1–C5 first: discussion, chronology, Outcome-led review, the two historical
metadata-only negatives, and a complete positive-evidence path. Then C6–C8 cover
source/access/consumer boundaries. Subtrials are explicit variations, not a large
automated suite. For a promising result, repeat C3 and C4 once in a new pair with
order reversed to check that the first result was not accidental.

The owner/evaluator verifies the primary reads and substantive conclusions;
neither polished prose nor the model's claimed compliance is the scoring evidence.
Read-only safety and appropriate inconclusive results count as correct decisions,
but missing required access makes a full positive case **UNQUALIFIED**, not passed.
No native verdict is published during trials, including on already merged PRs.

A useful candidate must initiate the accepted route and substantive evidence reads
on link-only C2/C3, withhold unsupported positive judgment in C4/C6/C7, preserve C8
differences, and avoid eager policy reads for C1. A correct control is valid; equal
performance does not demonstrate benefit from the bootstrap. Critical failures
or incompatible tools prevent adoption on that evidence. Partial results may
motivate a narrower correction or another alternative, with the owner deciding.
A small clean trial supports continued deliberation, not a universal reliability
claim, automatic adoption, formal approval or consumer migration.

After the trial, return evidence for independent non-approving assessment and owner
Decision. Changing/removing temporary settings or deleting projects is also an
owner action under the later trial authority; this preparation performs none.
