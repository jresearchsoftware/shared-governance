# Manual Codex task handoff

This example uses this repository's current Issue/AGENTS authority. It is a local
client binding and authoring example, not a second Task charter, universal prompt
schema or automatic adoption of the candidate
[task-handoff protocol](../packages/development-governance/vibevm/vibespecs/protocols/task-handoff.md).
Task 14's current Issue separately admits its Step 1 implementation and qualification.

For governed work here, keep the repository Issue and explicitly linked canonical
decisions current. The owner-admitted work identifies its Step and purpose; local
test/fix iterations remain inside that effort. Future Step allocation, retries
and conversation reuse follow the current Issue's declared instructions. No
stage-versus-attempt counter is inferred from this example.

An execution prompt can be as short as:

```text
Task 14 — Step 1 — Shared Task Handoff Protocol
Repository: jresearchsoftware/shared-governance
Canonical Issue: https://github.com/jresearchsoftware/shared-governance/issues/14

Read the complete current Issue, its linked accepted evidence and applicable
repository governance. Execute the admitted Step end-to-end and publish one
reviewable PR with exact-result evidence. Preserve unrelated work and stop for
independent exact-head review within the Issue's current permission boundaries.
```

Add an existing PR/result link, exact starting revision or environment/model hints
only when needed for the next action. A copied prompt cannot preserve authority
against later canonical decisions. Read current Issue/PR/review state and Git
facts before continuing; safely reconcile useful task work without replacing an
existing candidate. If the action or previous mutation is unclear, preserve work
and stop at that concrete boundary.

Use the supported Codex chat-title tool where available, then read the title back.
If rename or read-back is unavailable, state that limitation and retain the
Task/Step/purpose plus Issue link in a supported visible navigation aid. A prompt
does not prove the client's model/effort settings changed. Subagents supply bounded
implementation assistance only where permitted; they cannot enlarge scope or
provide this candidate's independent acceptance.

Commit substantive source and repository-accessible qualification evidence on
the task branch, use ordinary non-force push, open/update the reviewable PR,
and read its head back. Publish one English Outcome in the canonical Issue with
exact result, evidence, limitations, remaining work and review boundary. Analysis
or no-change work can instead identify its durable result without an empty commit.
CI is evidence; independent exact-head acceptance and owner integration remain
separate. One account copying a separate evaluator's assessment does not create
native approval or authenticate a distinct reviewer. Preserve the repository's
existing independent-review requirements.

Task 14 ends at that PR/Outcome handoff. Its admission authorizes no self-approval,
merge, package publication, consumer change, installation or Issue closure. A
future continuation follows the then-current Issue and review frontier, not this
dated example. [Self-adoption](self-adoption.md) describes the candidate/active
boundary; [Step 1 evidence](task-14/step-1/README.md) records the qualification.
