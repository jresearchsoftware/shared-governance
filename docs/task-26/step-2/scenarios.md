# Task 26 Step 2 — Outcome publication walks

These 12 desk-based applications use the proposed shared
[protocol](../../../packages/development-governance/vibevm/vibespecs/protocols/task-handoff.md)
and [manual binding](../../manual-task-handoff.md), with the facts below.
P and Q are distinct result PRs; A and B denote immutable result revisions,
not fabricated real SHAs. No Relay service, identity, schema or residual consumer
rule supplies missing behavior. PASS means applying the candidate to the stated
input yields the recorded target/decision and rejects the counterexample.
This is authoring evidence, not automated enforcement, model execution or
independent acceptance. No fixture Outcome is published externally.

| Walk / complete terminal Step result | Applied target and observable boundary | Rejected counterexample / result |
| --- | --- | --- |
| R1: Manual analytical Step returns a report and warnings; no PR exists or is intended. | One attributable Outcome on the canonical Task Issue, identifying the report/revision and limits. No empty commit, fabricated SHA or artificial PR. | Missing PR always blocks a genuinely known no-PR result. PASS. |
| R2: Issue Decision admits execution; that Step creates P and returns only P at A, with tests and committed documentation/evidence supporting it. | Exactly one top-level P conversation Outcome; link the Task/Decision through P's ordinary body/navigation and read the comment back. | Launch/admission through Issue requires an Issue Outcome, or supporting evidence makes a second Task-level result. PASS. |
| R3: The Task has P, Q and historical unrelated PRs, but this Step corrects only P from A to B. | One P Outcome at B. New post-terminal authorized execution has a new Step; review B freshly. | Count all Task PRs and route to Issue, or reuse A's acceptance for B. PASS. |
| R4: This Step returns P at A plus a substantive independent Task-level operational/research result outside P. | One Task Issue Outcome covers both, with P's exact A/status and the separately identifiable result/limits. | R6: Executor intends a single-PR result, but two conflicting candidate links leave its actual PR unresolved. | Stop publication and reconcile intended result-to-PR mapping; preserve work. No PR or Issue Outcome until resolved. | Silently fall back to Issue or guess one PR. PASS. |

Observed semantic result: 12/12 PASS. The prior
[26 lifecycle/acceptance walks](../step-1/scenarios.md) remain applicable: routing
does not change terminal Step allocation, chronological authority, minimal prompt,
warning disclosure, Direct/Deliberative selection, unchanged-result proof reuse
or stronger independent-review/identity boundaries. S7's recovery now expressly
reconciles an existing Outcome before any publication; it never permits duplicates.

The actual Step 2 has only the correction, generated candidate and supporting
qualification in PR #27. The owner's
[explicit publication exception](https://github.com/jresearchsoftware/shared-governance/issues/26#issuecomment-6127651575)
authorizes its one Outcome on that PR while candidate rules remain unaccepted.
The PR body/owner-linked CR and the Task Decision already provide navigation;
no duplicate Issue Outcome or status synchronizer is needed.
