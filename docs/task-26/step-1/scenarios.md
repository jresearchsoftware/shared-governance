# Task 26 Step 1 — semantic and behavioral walks

These 26 desk-based applications use only the proposed shared
[protocol](../../../packages/development-governance/vibevm/vibespecs/protocols/task-handoff.md)
and [manual binding](../../manual-task-handoff.md), plus the facts in each row.
No Relay rules, typed schema, reservation, label or service supplies missing
semantics. A and B identify immutable results, not invented real commit SHAs.
Each walk was checked against its stated counterexample during authoring; PASS
means the candidate yields the recorded decision and rejects that counterexample.
This is bounded implementation evidence, not automated policy enforcement,
fresh model/client execution, downstream adoption or independent acceptance.

## Charter, Step and minimal handoff

| Walk / input events | Applied decision and observable boundary | Rejected counterexample / result |
| --- | --- | --- |
| S1: Private backlog placeholder; owner clarifies goal/criteria before execution; no substantial discussion. | Consolidate into a clear body charter. No execution, no Step; preliminary editing needs no separate Decision for each thought. | A Step or typed Decision for every draft edit. PASS. |
| S2: Public backlog has substantive contributed alternatives and owner reasoning before execution. | Consolidation is allowed only with meaningful discussion, attribution and decision provenance preserved/linked; choose a separate Decision when consolidation would hide them. Still no Step. | Erase discussion because execution has not begun, or mechanically prohibit all body refinement. PASS. |
| S3: Owner authorizes first execution against charter C; executor begins Step 1; later owner adds material requirements. | C is historical from first execution, before any Outcome. Append the authorized change chronologically as a Decision; only non-semantic body edits remain permitted. | Freeze only after first Outcome, or prepend new requirements to C. PASS. |
| S4: Active Step 1 investigates, codes, fails a test, fixes it, reruns, receives ordinary clarification and returns Outcome A. | All work before the terminal handoff remains Step 1. Coding/testing need no separate admissions merely as ceremony. | Steps per test pass, commit, phase or clarification. PASS. |
| S5: Outcome A on PR P; review finds F1; owner Decision admits corrections; executor updates P to B. | New authorized execution is Step 2 even with the same purpose, branch, conversation or PR. Read A, F1 and Decision; review B freshly. | Same Step because P/goal persisted, or compulsory new PR. PASS. |
| S6: Step 2 returns BLOCKED with useful partial evidence; owner later authorizes another execution after resolving access. | New execution is Step 3, retaining prior evidence and BLOCKED history. | Reuse Step 2 merely because work was blocked, or renumber from 1. PASS. |
| S7: Step 3 result publication fails after execution; supported recovery republishes exactly that result without executing again. | Preserve Step/execution/result identity; reconcile uncertain external publication before replay. | New Step for transport recovery, or silently execute again as replay. PASS. |
| S8: Independent review, owner discussion, strategy Decision and merge occur after Outcome; no new execution is handed off. | No Step increment. A Decision may direct future work, but numbering advances with its newly authorized execution handoff. | Advance Step on every Decision, approval or merge. PASS. |
| S9: C permits scope X; D1 admits Y; later authorized D2 explicitly revokes Y and supersedes a D1 completion condition. | Effective authority is C plus still-applicable D1 parts and D2; revoked Y cannot be executed. Read all chronological records, not only the latest comment/body. | Discard C and all D1 wholesale, or retain revoked Y. PASS. |
| S10: Task closed after accepted Step 3; owner reopens with reasons and admits additional work. | Preserve charter/results/acceptance; append new Decision and execute Step 4. | Rewrite charter, reset Step or retroactively revoke acceptance merely on reopening. PASS. |
| S11: Outcome recommends larger scope; review agrees; ordinary discussion requests it without authorized admission. | Evidence informs owner disposition but supplies no scope permission. No fresh execution until authorized; PR-specific findings do not silently amend Task authority. | Treat a recommendation/review/chat as an admitted Task amendment. PASS. |
| S12: Complete charter, Decisions, Outcomes/reviews and checks are linked; local handoff uses the manual example plus a genuinely unavailable starting-worktree hint. | Header/link/start instruction navigate to complete chronology; no copied goals, test matrix, prohibitions, profile or publication contract. Explicit accepted-SHA Task binding remains independent of candidate prose. | Duplicate the Issue checklist, read only body, or let candidate AGENTS choose its own acceptance. PASS. |
| S13: A non-GitHub project uses a durable tracker charter and linked chronological Decisions; one account publishes a separate evaluator's assessment. | Execution-cycle/authority/strategy semantics still work without Relay or GitHub. Native distinct-reviewer identity is unproved; if project policy requires it, acceptance waits. | Require Relay/JSON, fabricate native approval, or let the implementer self-accept. PASS. |

## Acceptance strategy and verdict publication

| Walk / input events | Applied decision and observable boundary | Rejected counterexample / result |
| --- | --- | --- |
| A1: Agreed bug fix; no override; independent review of A passes all required checks; safe squash merge is already authorized locally. | Shared default Direct allows real exact-result APPROVE followed by authorized merge. Closure/deployment still require their own satisfied conditions. | Add owner discussion as an obligatory extra round to every fix, or infer all permissions from approval. PASS. |
| A2: Technical research compares app-server architectures; positive exact-A review; owner has not discussed alternatives. | Shared default Deliberative: substantive non-approving preview includes findings/warnings; no APPROVE and no approval-driven merge yet. | Treat code/research quality as owner architecture selection or publish approval before discussion. PASS. |
| A3: After A2 the owner discusses and explicitly accepts report quality, rejects its recommendation and authorizes acceptance of unchanged A. | Revalidate A/current authority/checks and publish permitted report approval using sufficient independent evidence. No implementation, migration, install or release of the rejected design. | Require adopting the recommendation to accept a good report, or infer adoption from report acceptance. PASS. |
| A4: Deliberative report A has a real unsupported claim affecting its recommendation. | Non-approving review identifies claim, impact, correction and required evidence; a genuine change request is appropriate under local mechanisms. A defect-free report instead receives a non-approving assessment, not fake defects. | Fabricate REQUEST_CHANGES/holds solely to inhibit auto-merge. PASS. |
| A5: Positive independent exact-A assessment exists; owner discussion/Decision accepts A; head and effective authority/checks/identity remain current. | Reuse sufficient review evidence; actual exact-A APPROVE may be published without duplicate complete review. No new execution, no new Step. | Force a complete second review or allocate a Step solely for approval publication. PASS. |
| A6: Between preview and owner acceptance, A changes to B. | Assess B freshly for changed behavior, prior findings and adjacent/new risks; A's acceptance cannot transfer. Fresh authorized rework after terminal Outcome has the next Step. | Approve B by reusing exact-A acceptance merely because the owner liked A. PASS. |
| A7: Task Decision explicitly selects Deliberative for an otherwise ordinary correction; project default is Direct. | Owner-authorized Task selection wins; withhold formal approval until the selected discussion/Decision boundary. Independent checks remain required. | Project/default classifier overrides explicit Task authority. PASS. |
| A8: No Task selection; project has an adopted additional strategy, Design panel, requiring an independent preview and named stakeholder discussion. | Applicable project extension wins over shared default while preserving owner/trust boundaries, independent assessment and checks. No universal enum/schema is needed. | Ignore legitimate extensions or let a new name waive required review. PASS. |
| A9: No Task/project selection: one result asks an architecture choice in code; another corrects agreed governance wording in documentation. | First defaults Deliberative; second Direct. The required acceptance decision governs, not file type. | Classify all code as Direct or all governance/docs as Deliberative. PASS. |
| A10: Report combines a fixed defect and an unresolved material policy choice; current strategy is ambiguous. | Resolve the material need for owner deliberation before formal APPROVE; substantive preview can proceed. No fake approval or new execution just for discussion. | Guess Direct because some checks pass, or add a permanent classifier service. PASS. |
| A11: Project plans APPROVE immediately for research but sets a post-approval continuation hold. | This fails the Deliberative boundary: hold acts too late. Keep the verdict non-approving until discussion/Decision; later genuine approval can use existing authorized continuation. | Claim a hold prevented premature APPROVE, or redesign merge machinery here. PASS. |
| A12: Before acceptance the owner explicitly revises Deliberative to Direct after the necessary result choice/criteria are settled. | Apply the authorized Decision, revalidate effective authority/head and preserve independent review/checks/trust requirements. Revision does not retroactively make a premature verdict compliant. | Forbid all authorized revisions or let an arbitrary comment weaken identity/checks. PASS. |
| A13: Head A is unchanged but owner authority/check requirements changed after preview, or native approving identity is unavailable. | Reconcile current authority and required checks/identity before publishing actual approval; reuse only still-sufficient evidence. Disclose gaps; owner-account text headed APPROVE is not native approval. | Treat unchanged SHA as sufficient irrespective of changed authority, or substitute advisory publication for required native identity. PASS. |

Observed result: 13 lifecycle/handoff walks and 13 acceptance walks pass the
stated semantic criteria. The exact candidate report binds these walks to their
reviewable Git result. They introduce no standing CI policy simulator, state
machine or downstream automation. Existing exporter/integrity/release regressions
separately exercise actual files and recovery.
