## Placement, compatibility and cost

A single opt-in topic is the smallest coherent placement. Widening TH would
attach broad context/instruction ownership to projects that adopted execution
handoff alone. Widening SA would both miss ordinary consumers and broaden its
producer-specific accepted-source contract. Widening IR would tie general
startup to independent assessment while missing implementation/contribution.
Keeping the rule only in this producer's AGENTS would leave the exported gap.
Splitting those clauses across existing topics would also hide which new
obligations a consumer was accepting.

The candidate advances the whole package from **2.4.0 to 2.5.0 MINOR** under
[accepted package-versioning](https://github.com/jresearchsoftware/shared-governance/blob/9bd05c89f15e6c83a3d84f68368d7a8ef50f3119/packages/development-governance/vibevm/vibespecs/protocols/package-versioning.md#contract-and-version-classification).
Compatibility depends on explicit adoption, unchanged existing mandatory
behavior and retained local authority, not merely on adding a file. The eight
existing protocols retain their accepted text. This producer's root adoption
set, local/custom bindings, shared ChatGPT tools and generated Instructions are
not broadened. Installing a complete new slot makes the ninth topic available;
its conditional boot pointer does not activate it for an existing consumer.

For an adopting project, the duty is to read enough authoritative material for
the next decision and refresh facts whose validity changed. There is no numeric
file/token/tool-call budget or forced reread ceremony. The cost is ordinary
source/authority inspection; avoiding unrelated preload and unchanged repeated
reads reduces unnecessary work without a model-efficiency claim. Existing
required checks, full review, permission boundaries and source completeness
remain intact. The topic adds no cache service, parser, context ledger,
automatic settings operation or extra owner action. Any future mandatory
retrieval/control machinery would need its own authority and proportionality
justification; this Task implements none.

This is source authoring and native materialization only. It edits no Relay or
other consumer and performs no topic adoption, manual package publication,
approval, merge, closure, live settings/Sources, credential or PROD operation.
Any later Relay migration must reconcile its reusable duplicates with the
accepted pinned shared topic in the same separately authorized change, retaining
all product bindings above. Residual Relay instructions are not used to supply
the candidate's portable obligations.

## Qualification and review boundary

Source/export, native routing/slot integrity, distribution, release/version,
self-adoption and affected regression checks bind their results to the actual
candidate. Use the accepted disposable workflow to qualify pinned VibeVM
materialization. Optional native publisher/resolver integrations, skipped
tests and actual client/model behavior must be reported separately from passes.
No static text scenario can supply missing primary runtime or independent-review
evidence.

The canonical PR Outcome records the exact remote head, retained primary check
results and material warnings, skips and limitations. The implementation helpers
and these semantic walkthroughs supply implementation evidence only. Independent
substantive exact-result NON-APPROVING assessment and the owner's policy/placement
Decision remain the next acceptance boundary; green checks and source completion
do not imply adoption, publication, integration or closure.
