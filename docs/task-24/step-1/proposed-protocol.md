# Proposed shared self-adoption protocol

**Design draft for Task 24 owner disposition and independent review.** This file
is not exported Development Governance, adopted instructions or evidence of a
working producer migration. Packaging it and replacing this producer's current
implementation remain pending the decision described in the [report](README.md).

## Applicability and authority

Apply self-adoption only where a producer consumes some of the guidance or agent
Skills it authors, and where the owning project explicitly adopts this topic.
Other projects ignore it. Installation, a dependency update or a new protocol
file does not activate it. Preserve the project's local overlays and separate
execution, acceptance, integration, publication, installation and closure rights.

Develop and independently assess a candidate under guidance from an identifiable,
independently accepted source-main commit. Freeze that identity for the current
effort or review as appropriate. Source acceptance and public package publication
are distinct events. A producer can use accepted source before public release
unless its local product contract explicitly requires publication. Other
consumers retain their own adoption and compatibility decisions.

Candidate branch instructions, authored rules, generated boot and Skill
projections are proposed content. They may be installed, regenerated, diffed and
tested in development; they must not silently become the instructions governing
their own development or review. Bind accepted instruction discovery through the
host's supported launch/handoff mechanism independently of candidate-controlled
files. A sentence inside candidate AGENTS telling the agent to read main is not
an enforceable loading boundary. Disclose unsupported clients or unresolved
loading behavior; do not claim protection from arbitrary malicious candidate code.

## Native materialization and ready state

Prefer the host's ordinary package manager/materializer or native Skill installer.
Use stable source inputs, exact provenance, conditional routing and safe rollback;
preserve human-authored overlays. Do not prescribe a custom resolver, mandatory
service, registry, global policy engine, update ledger, model gate or universal PR
policy. A demonstrated tool gap needs a bounded project-owned disposition before
replacing an already verified mechanism.

For the adopted source-controlled producer layout, commit materialized
dependencies and generated agent/boot routes with their authored changes in one
reviewed candidate. An accepted clean checkout must contain functioning applicable
guidance without first downloading dependencies, running a materializer or
executing bootstrap code. Ordinary execution reads that accepted state; deliberate
development/maintenance performs materialization. Pull/checkout advances source
and its projection together. The owning project's normal validation detects
missing, stale, conflicting or mismatched source, slot, lock and routing output.
Do not infer completeness from a package-manager exit code alone.

Author and materialize before independent exact-head review. Review source,
generated differences, semantic coverage, the accepted authority snapshot and
available validation together. A changed approved head needs the applicable fresh
qualification and review. No special just-before-merge hook or separate
post-publication adoption PR is required.

## Qualification and recovery

Use structural checks and simple scenarios by default. When model behavior needs
qualification, feed the candidate guidance to an isolated disposable probe; do
not promote it into the primary developer or reviewer session. Probes supply
implementation evidence, not independent acceptance. No persistent TEST
environment or extra approval framework is required by this protocol.

Reject partial or corrupted activation and preserve accepted guidance. Diagnose
producer/source/slot/index mismatches using the existing materialization and Git
evidence. Retry through the supported path after recovery. For committed outputs,
ordinary Git restore/revert supplies rollback; do not rewrite frozen releases.
An unavailable public publication is not revocation of an independently accepted
source change. Report concrete gaps and obtain the owning project's disposition
where a supported replacement cannot meet the adopted contract.
